# AGENTS.md - Poketto Repository Guide

Scope: This file governs the entire repository.

## Project Overview

**Poketto** is a cross-platform Visual Novel Game Launcher built on
**Tauri v2 + SolidJS + Rust**:

- **Frontend**: SolidJS + TypeScript + Tailwind CSS v4 (`src/`, Vite)
- **Backend**: Rust in `src-tauri/` (Tokio async runtime, `redb` VNDB
  cache, JSON stores)
- **APIs**: VNDB API integration (search, details, characters, user list),
  Discord Rich Presence
- **Targets**: Linux (Wayland/X11) and Windows (NSIS installer +
  auto-updater)

There is no Slint code in this repository. NEVER introduce `.slint` files,
Slint dependencies, Slint callbacks, or Slint-Rust bridges here; the Slint
rewrite lives in a separate repository.

## Intent & Principles

- **SOLID, KISS, YAGNI** - Keep it simple and avoid over-engineering
- **Cross-platform first**: Linux (Wine/Proton) and Windows paths must
  both be considered; gate Linux-only code with
  `#[cfg(target_os = "linux")]`
- **Offline-capable**: Core library/launch flows work without internet;
  VNDB failures degrade to cached data with a clear English message
- **Testability**: Pure functions where possible (`src/utils/` is the
  frontend example with vitest coverage)
- **Clarity**: Idiomatic naming, minimal comments

## Expectations for Agents/Contributors

- Keep changes small and focused; one feature per PR
- Run the gates covering what you touched before committing (see
  Development Commands)
- NEVER hand-edit `src/bindings.ts`: it is generated by tauri-specta on
  debug builds
- NEVER add features, fix bugs, or regenerate bindings outside the
  `src/` + `src-tauri/` contract described here

## Code Organization

```text
poketto/

├── src-tauri/                  # Rust backend (commands, models, db, wine)
├── public/                     # Static assets (icon.png, fonts)
├── index.html                  # Vite entry
```

### File Layout Rules

- Backend domain modules stay grouped by feature under
  `src-tauri/src/` (`commands/`, `wine/`); shared types live in
  `models.rs`
- Frontend follows existing colocations: `views/` per route,
  `components/` shared UI, `context/` providers, `hooks/` reusable logic,
  `utils/` pure helpers with `*.test.ts` coverage

## Workflow & Quality

### Development Commands

```bash
npm install
npm run dev            # Vite frontend only
npm run tauri dev      # Full desktop app
npm test               # vitest run
npm run build          # Frontend bundle (also used by Tauri bundling)
cd src-tauri && cargo check
cd src-tauri && cargo clippy -- -D warnings
cd src-tauri && cargo test
```

Run Rust commands through the rustup toolchain (`rust-toolchain.toml`,
`~/.cargo/bin` first in `PATH`). System cargo with a version-skewed
clippy (e.g. Fedora rustc 1.98 + clippy 1.95) fails with E0514; that is
an environment bug, never a code bug.

### Dependency Rules

- Frontend versions are pinned in `package.json` / `package-lock.json`;
  backend versions are pinned in `src-tauri/Cargo.toml` /
  `src-tauri/Cargo.lock`. NEVER use `"latest"`; unpinned versions break
  reproducible builds.
- Backend `Cargo.toml` MUST NOT gain path dependencies outside
  `src-tauri/`.
- The `discord-rich-presence` dependency is pinned to a git rev; do not
  bump it to crates.io without verifying the IPC API still builds.

### Error Handling

- Fallible backend operations return `AppResult<T, AppError>`
  (`src-tauri/src/error.rs`, `thiserror`). `AppError` serializes as
  `{ kind, message }` for the frontend.
- Add `From` impls for new error sources; keep user-facing messages in
  plain English.
- Validate destructive inputs (game paths, wine binaries, VNDB tokens)
  and return `Validation` / `NotFound` / `AuthRequired` variants rather
  than panicking.

### Database & Persistence Rules

- Stores: `games.json`, `settings.json`, `daily_playtime.json` (JSON) +
  `vndb_cache.redb` (`vn_cache`, `char_cache` tables, bincode payloads).
- All JSON writes go through `atomic_write` (temp file + rename); NEVER
  write store files directly.
- Read caches in order: in-memory `HashMap` -> `redb` disk cache ->
  network; persist fresh network results to both cache layers.
- `load_games()` failure MUST fall back to an empty library, never crash
  startup; `load_settings()` falls back to defaults.

### IPC Rules (Tauri Commands)

- Every command is `#[tauri::command]` + `#[specta::specta]`, re-exported
  from `src-tauri/src/commands/mod.rs`, registered in
  `collect_commands![...]` in `lib.rs`, with its types added via
  `.typ::<...>()`.
- Debug builds regenerate `../src/bindings.ts`; commit the regenerated
  file together with the backend change. NEVER edit it by hand.
- Shared mutation goes through managed `AppState`
  (`parking_lot::Mutex` fields); clone out of the lock before awaiting.

### Frontend Rules

- Consume backend types only from `./bindings`; do not redeclare IPC
  shapes locally.
- Global server state lives in context providers (`GameContext`,
  `SettingsContext`, `VndbContext`); route-local filtering lives in
  hooks (`useLibraryFilters`, `useUpdater`).
- Pure logic (formatting, validation, blur gating, BBCode) lives in
  `src/utils/` with vitest coverage; every new util ships with a test.
- Styling is Tailwind utilities in JSX; icons come from `lucide-solid`.

### Test Structure

```text
src/utils/*.test.ts        # blur, formatters, validators
src-tauri/src/models.rs    # domain unit tests (mod tests)
```

### Code Quality Rules

- Handle errors gracefully with user-friendly English messages
- Never commit secrets or tokens (`.env` is gitignored)
- Keep the repo clean: generated artifacts are in `.gitignore`
- **DO NOT add comments to the code** - The codebase intentionally avoids comments. Code should be self-documenting through clear naming and structure. Do not add inline comments, block comments, or documentation comments unless explicitly requested.

### Priority Labels

- **P2**: Medium - nice to have, can wait

## Git Workflow

### Branch Strategy

- `main` - stable release branch
- Feature branches: `feature/<name>`
- Bug fixes: `fix/<name>`

### Commit Message Format (English only)

```text
<type>: <short description>

[optional body]
```

Types: `feat`, `fix`, `docs`, `refactor`, `chore`, `test`

### Pull Request Guidelines (English only)

1. Create feature branch from `main`
2. Make changes, verify with `npm test` and `cargo test` (in `src-tauri/`)
3. Commit with descriptive messages
4. Push and create PR via GitHub
5. Link related issues
